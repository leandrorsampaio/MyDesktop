# Changelog

All notable changes to this project are documented here, newest first.

| Version | Date       | Changes                                                      |
|---------|------------|--------------------------------------------------------------|
| 2.56.0  | 2026-08-29 | **Reports answer "what did I do" instead of "what is on my board".** A report was a board snapshot of every column, which is the wrong question for a weekly one-to-one — and it failed twice on real data: the Done column accumulates until you archive (so it spanned weeks, not the period), and anything **archived** during the week was missing entirely. Measured on the real profile: a 14-day window finds 19 completed items, 8 of them from the archive that the old report could never see. Reports now carry a **period** — from the previous report's timestamp, literally "since we last spoke", falling back to 7 days — and an **activity** breakdown of completed / advanced / created / attention, with `epicName` and `points` carried along. Archiving now stamps **`archivedDate`**, so completion is recorded rather than inferred from the last log entry (which records the last *move*). **The date-only trap:** log entries are `YYYY-MM-DD` app-wide, so a log-derived completion parses to midnight; compared against an exact period start of 15:20 today it ruled out everything finished that day, silently dropping a day of work. Day-precision stamps are now compared against the start of the period's day. **AI summary** (`POST /reports/:id/summarise`): grouping and counting stay in code — deterministic and free — while the model does the one thing code cannot, turning ticket titles into presentation bullets and merging related tickets into single lines. Output is grouped **by epic with its stakeholder attached**, plus an `attention[]` list for things to raise rather than report. Silo names are validated against epics actually in the report, so a hallucinated one cannot reach a document taken into a meeting. Fired **after** generation and never as part of it — the report must appear instantly and never fail on a missing model — with a *Regenerate summary* button on the same endpoint and **Copy as bullets** for pasting into slides. 14 new API tests. |
| 2.55.0  | 2026-08-29 | **AI page removed; staging moves to the backlog.** With the assistant floating on every page, the `/:alias/ai` page was half a worse copy of it — the same conversation (shared controller), a proposed-changes list the board preview does better, and a model selector that also lives in Config. Its one unique job, **staged tasks**, moved to the **backlog page**, where it belongs: a staged task is proposed work not yet committed to, which is what a backlog is — and it gives a months-stale backlog a second reason to be opened. An **AI staging** toggle sits at the right of the backlog header, collapsed by default (the backlog is the page's subject, not the assistant) and auto-opening with a count badge when something is already waiting. Inside: a roomy paste box — the one thing a 30vh floating panel is bad at — plus the staged rows with all five actions intact; promoting re-reads tasks so the item shows in the list below immediately. `/:alias/ai` **301-redirects** to the backlog, since unknown pages otherwise fall back to the board and an old bookmark would land there silently. Deleted: `ai-page.js`, 34 `.aiPage` CSS rules, the rail's lightning nav item and the `g i` chord. Two things caught after deletion: the staged rows lost their `--archive-col-actions: 300px` override (it had lived on `.aiPage`) and rendered cramped, and `<page-fab>` sat bottom-left — now the assistant launcher's spot — so it moved to bottom-right. |
| 2.54.0  | 2026-08-29 | **Assistant UX rework.** The dock was wrong: it was a layout feature (a resizable third grid track that squeezed the board) reachable only by a keyboard shortcut, with a separate *Ask AI* button inside each card. It is now a permanent **AI button, bottom-left, on every page**, which grows a panel out of itself on click. **Floats over everything** — `z-index: 1500`, above modals (1000) and below toasts (2000) — and reserves no layout space at all. **Stays in the bottom band** (30vh, max 50vh, anchored above the button) so the top half of the screen is never covered; `transform-origin: bottom left` plus a 180ms scale makes it read as coming out of the button, inside a `prefers-reduced-motion` guard. **Context is now implicit**, so the per-card *Ask AI* button is gone: `app.js` installs a context provider resolved fresh on every send (not when the panel opened — the user may have navigated since), sending `{ page, taskId }` where an open task modal wins over the page. The server re-checks both against real data before they reach the prompt and drops anything unknown, and tells the model to assume the conversation is about an open card. The panel header shows the resolved context ("About the board", `About "Refactor auth"`) — implicit context the user can't see would just be confusing. Removed: the grid-track rules, the drag-to-resize edge and its localStorage width, and `.taskForm__askBtn`. 5 new API tests. |
| 2.53.0  | 2026-08-29 | **AI assistant, phase 8 — streaming replies.** New `POST /:profile/ai/chat/stream` returns server-sent events — `text` deltas as the model writes, then one `done` carrying the same payload the buffered route returns, or `error`. **Kept as a separate endpoint rather than a flag** so `/ai/chat` stays intact as a fallback: not every OpenAI-compatible server streams correctly, and a stream that fails before producing any text costs a retry rather than the message (once text has arrived, a later failure is a real error and is reported instead). **Tool calls are not streamed** — both providers emit a tool's JSON arguments as fragments that are only valid once complete, so `ToolCallAccumulator` collects them by index and parses at the end, dropping any that never complete rather than throwing; all validation and persistence still happen before `done`. The two routes now share `prepareAiChat()` and `persistAiToolOutput()`, so they cannot drift on validation, prompt construction, which tools are offered, or what gets stored — extracting those removed ~80 lines of would-be duplication. `parseSseChunk()` carries the risk (a chunk can end mid-line or mid-event, and getting it wrong silently truncates output), so it is a pure function with 12 tests, including one that feeds a payload one character at a time and one asserting every chunk size parses identically; source of truth in `utils.js` with the standard duplicate note in `server.js`. Client rendering is coalesced onto an animation frame, since re-rendering the transcript per token is far too much work per frame. Also tightened: the dock's notice now records *why* it is showing (`dataset.kind`) instead of sniffing its own message text, so rewording a string can't silently break the clearing logic. Verified end to end against a mock provider that splits a tool call across three fragments. 12 new unit tests. |
| 2.52.0  | 2026-08-29 | **AI assistant, phase 7 — memory.** A short curated list of durable facts about how you work (`ai-memory.json`, per profile) injected into every system prompt — what lets story points and epic conventions compound across sessions instead of resetting. **Deliberately a plain, hand-editable JSON list, not an embedding store:** "your data, your machine" has to mean a file you can read, edit and version, and a vector database would break the zero-dependency rule besides. **The AI may propose, never add** — a third chat tool, `propose_memory`, stores entries with `approved: false`; they are shown for review but `renderMemoryForPrompt()` skips them, so nothing reaches a prompt until approved on the config page (and approval can be revoked). Duplicates are dropped before storing. Limits: 40 entries, 300 chars each, plus a separate 4000-char prompt budget, since memory rides along with the board snapshot on every message; the whole section is omitted when nothing is approved rather than emitting an empty heading. New "What the assistant remembers" block under Config → AI Assistant: unapproved suggestions sort to the top and render dashed (the same not-committed-yet vocabulary as pending attachments and previewed cards) with a *Remember this* button; approved entries are labelled `yours` or `suggested` and edit inline on blur. One bug caught in verification: the test-only `/ai/_test/prompt` endpoint didn't load memories, so it reported a prompt the model never saw — it now loads exactly what the chat handler loads. 16 new API tests. |
| 2.51.0  | 2026-08-29 | **AI assistant, phase 6 — the dock.** The assistant becomes a panel beside the board instead of a page you navigate to. `a` opens it from anywhere; so does a new *Ask AI* button in the task modal's tab strip, seeded with that task's title but deliberately **not sent** — an entry point starts the sentence, it doesn't speak for you. The `/:alias/ai` page stays for long paste-a-transcript sessions. **It squeezes rather than covers:** the board must stay visible and interactive during review, so the dock is a third track in the `.appShell` grid (`body.--assistantOpen` switches the template to `48px 1fr auto`), resizable by its left edge and remembered in localStorage. **One conversation, two surfaces** — new `js/assistant-chat.js` owns the transcript, pending placeholder, token accounting and persistence; the dock and the AI page both subscribe to it. That is a correctness fix, not tidiness: both surfaces live on the same page, and two copies of the history would each PUT the whole transcript and clobber each other. The AI page was refactored onto it, deleting its private history, usage and availability state. **The empty state is the point of the phase** — new `js/assistant-suggestions.js` turns the live board into at most three facts with a verb attached ("1 card past its deadline → Triage them"), computed locally with no AI call so they render with the assistant switched off; clicking one sends it. Rules fire in priority order and any that find nothing are dropped, so a tidy board says little. **Three ordering bugs caught in verification:** `assistantChat.init()` ran before `setApiBase()` and so fetched an unscoped URL; `refreshAssistantSuggestions()` ran in `initBoardEventListeners()`, which is before `setColumns`/`setTasks`, so it always saw an empty board; and the dock's `flex-basis` did nothing because the shell is a grid, not a flex row — main was losing 8px instead of 380. | 2.50.0  | 2026-08-29 | **AI assistant, phase 5 — board preview.** Pending proposals render **on the board, where they would land**, rather than as a list you have to simulate in your head. A bar under the header appears whenever proposals are pending; *Preview on board* enters the mode, `Esc` or *Exit preview* leaves. Updates get a dashed border and a caption (`size → 8, mark priority`); a move dims the origin card and puts a dashed accent-bordered **ghost at the top of the destination column** captioned `from To Do`; a delete goes red and struck through; untouched cards dim to 0.4 so the changes are what the eye lands on. Each annotated card carries ✓/✕ for a per-card decision, and the bar carries Apply all / Discard all. **It annotates rather than simulates** — applying every proposal to a copy of the board would mean a second implementation of the server's `applyProposal()` living in the client, which is the duplication Code Rule 3 exists to prevent and a place the preview could quietly start lying; moves get the spatial ghost because that is the case where position carries the meaning. Rejecting one proposal then just drops its annotation, with nothing to re-simulate. New `public/js/board-preview.js` holds the pure half (tasks + proposals → per-column plan; no DOM, no fetch) with 15 unit tests; `app.js` owns the DOM half. **Two bugs caught in verification, both from the v2.43.1 card reconciler:** preview styling was initially a host class toggled inside `task-card.render()`, which the reconciler strips (it syncs `data-*` but only keeps classes the renderer set) — so all preview styling now keys off `:host([data-preview="…"])`; and `card.draggable = false` only affected freshly created cards because the reconciler deliberately leaves `draggable` alone, so dragging is blocked in the dragstart handler instead. | 2.49.0  | 2026-08-29 | **AI assistant, phase 4 — proposed changes.** The assistant gets its second verb: `propose_tasks` creates new work, `propose_changes` edits work that already exists — re-filing, rescheduling, resizing, moving between columns, removing duplicates. **Nothing proposed reaches the board.** Changes land in a review buffer (`ai-proposals.json`, per profile, capped at 50) and only an explicit apply moves anything; there is a test named after that guarantee. Proposal shape: `{ id, kind: 'update'|'move'|'delete', taskId, payload, reason, createdAt }`. **There is deliberately no `create` kind** — new tasks already have a reviewable flow in AI staging where they can be edited, cloned and promoted, and a second creation path would be worse, not richer. **Validated twice on purpose:** `normaliseProposal()` drops anything referencing a task, column, epic or category the profile doesn't have (a buffer full of un-appliable rows is worse than a shorter honest one) plus updates that would change nothing; then `applyProposal()` re-runs `validateTaskInput` / `validateMoveInput` **at apply time**, because the board may have moved on since the proposal was written. It shares the *validators* with the hand-driven routes rather than the handlers, and mirrors their log entries. A stale proposal returns `409 { discarded: true }` and is dropped rather than re-offered; `apply-all` reports per-proposal failures instead of aborting the batch, since each is an independent decision the user already made. New `<proposal-row>` component renders each change as a readable sentence (`size → 8, mark priority`, `→ In Progress`, `Remove from the board`) with its reason, in a Proposed Changes section on the AI page that hides entirely when empty; `delete` is the only verb that gets colour, being the only irreversible one. The provider callers now take an **array** of tools, so one turn can both propose tasks and propose changes. 17 new API tests. One phase-1 test was rewritten: it asserted the exact prompt wording rather than the property, and broke when the two-tool paragraph replaced it. |
| 2.48.0  | 2026-08-29 | **AI assistant, phase 3 — story points and epic contexts.** Both are plain data with manual UI: fully usable with the AI switched off, and the substrate later phases reason over. **Story points** — new nullable `task.points`, one of `1, 2, 3, 5, 8, 13`. A deliberately short scale: 1 is "do it now", 13 is "one to two days" and is the ceiling. **There is no 21** — anything bigger is a split, not a larger number, and splitting is the primary job points do in a single-user tool. The server rejects 4, 7, 21 and friends; the ceiling pill is dashed in the UI to say where the scale stops. **No velocity, burndown or sprint reporting is built on these and none should be** — that is team ceremony. Toggleable pills in the task modal (click the selected value again to clear, matching the epic pills, which is why the toggle logic was generalised over both groups), and a tabular-figures chip on the card with no colour, since colour means epic and priority. Points ride in the AI board snapshot and the classifier may suggest one during quick capture. **Epic contexts** — new optional `stakeholder`, `cadence` and `expectations` on the Epic model (500 chars each), edited on the config page with auto-save on blur. An epic was a name and a colour; the pain epics were meant to solve is *silo switching* — different stakeholders, different expectations, different conversations — which is data the model never had. When set they render into the system prompt beneath the epic so the assistant can reason about stakeholders rather than topics; when unset they are omitted entirely, so older profiles don't pay for empty labels. `validateEpicContext()` / `applyEpicContext()` are shared by the create and update routes so the two can't drift. The config epic row became two stacked rows (`__itemMain` + `__itemContext`), the context grid collapsing to one column under 720px. 15 new API tests. |
| 2.47.0  | 2026-08-29 | **AI assistant, phase 2 — quick capture.** `c` from any page opens a one-line bar; type, Enter, done. Solves the hallway-conversation problem: filing a note properly costs more attention than is available in the moment, so it never gets written down. **Two requests, deliberately.** `POST /:profile/capture` creates the task and returns — **no AI call at all**, which is what makes it instant (~17ms measured) and unconditionally reliable; it lands at the top of the first non-backlog column with `needsFiling: true`. `POST /:profile/tasks/:id/classify` is the slow optional half: epic, category, priority, destination column, deadline, and an optional title rewrite (the original wording moves to the description — a captured note is the user's own words and is never discarded; over-long notes spill into the description rather than being truncated). The toast carries an **Undo**, and an `unfiled` chip marks the card for a later review pass. Classification output is advisory — every field is validated against the profile's real epics/categories/columns, and `hasArchive` columns are excluded as destinations. New `<quick-capture>` component (not a modal: a dialog asks to be read, this takes a line and disappears). `toast-notification` gains an optional inline action (`show(msg, type, duration, {label, onClick})`), forwarded through the success/error/info/warning wrappers. `buildClassifyPrompt()` is board-free by design — it runs on every note and must stay cheap; the provider callers were generalised to accept any tool. **Two bugs caught in verification:** the optimistic insert collided with an existing `position: 0` because the server's column shift wasn't mirrored client-side (card rendered in the wrong slot); and the toast convenience wrappers dropped the new 4th argument, so Undo never rendered. 12 new API tests. |

| 2.45.0  | 2026-08-28 | Feature: **File attachments on tasks.** Drop files onto a card on the board, or drop/paste/browse from the new **Files** tab in the task modal — Print Screen then Ctrl+V attaches a screenshot in one gesture. Attachments work on board, backlog, archived and AI-staged tasks: they are keyed by task id alone, so archiving, restoring and promoting carry the files along with no copying. **Transport — raw bytes, no multipart:** `fetch` is handed the `File` as its body verbatim, with the type in `Content-Type` and the percent-encoded filename in `X-Attachment-Name`. That avoids writing a multipart/form-data parser entirely. `mini-server.js` gains `app.raw(pattern)`: matching requests skip body parsing and arrive as `req.rawBody` (a Buffer) under a larger 16 MiB outer cap — the previous `.toString('utf8')` would have corrupted every binary payload, since a PNG is not valid UTF-8. `res.sendFile` no longer overwrites a Content-Type the caller already set, matching what `res.json`/`res.send` next to it already did. **Storage:** bytes go to `data/{alias}/attachments/{taskId}/{attachmentId}{ext}` (gitignored, mode 0600, written tmp-then-rename like `writeJsonFile`); metadata rides on the task object as `attachments[]`, the way `log` does — so `GET /tasks` already carries everything the paperclip badge needs, and export picks it up for free. The user's filename is **never** a path component: files are named by generated id plus an extension from the MIME allowlist, and the original name is kept for display only. **Security:** `image/svg+xml` is deliberately outside the allowlist — a same-origin SVG can run script against the app — so it stores as `application/octet-stream` and can only be downloaded; every response carries `X-Content-Type-Options: nosniff`; `Content-Disposition` is `inline` only for images/PDF/text (`?download=1` forces otherwise) with quotes stripped from the ASCII fallback and the real name in `filename*`. **Limits** (three constants at the top of server.js): 5 MB per file, 20 files per task, 200 MB per profile, the last measured from disk so orphans still count. **UI:** the task modal's main column gains a Description/Files tab strip with a count badge; images preview as thumbnails and open in a stacked viewer modal, text and code render in a `<pre>`, PDFs in an iframe, anything else is download-only. Code files (`.js`, `.py`, `.sql`, …) are uploaded as `text/plain` regardless of what the OS reports for `File.type` — otherwise they would store as opaque binaries and lose their preview. Adding a *new* task queues files in memory with object-URL previews and flushes them once the server returns a real id. Cards, backlog rows and staged rows show a paperclip + count; expanded archive rows list their files as download links. `kanban-column` drag handlers now bail out when `dataTransfer.types` contains `Files`, so a file drop never draws a drop indicator or tries to move a task. 19 new API tests, including a byte-for-byte binary round-trip. |
